# v1.7 Design — Due-date visibility, onboarding tutorial, interactive streak gifts

**Date:** 2026-08-30 · **Status:** Approved by user · **Scope:** three user-facing releases (v1.7.0–v1.7.2) opening Phase 7

All paths below are relative to `butter/`.

## Context & decisions made during brainstorming

- **Phone notifications are deferred to native.** The app is a static SPA on GitHub Pages
  with no service worker and no backend; real push is impossible without both. The native
  milestone in ROADMAP already owns due-date reminders — the in-app popup ships now, and its
  selection logic is written as a pure helper so native scheduling reuses it unchanged.
- **Milestone chests are already once-ever** (Phase 5f, `game_state.claimed_chests`). A reset
  streak that re-reaches a milestone does not re-pay. This work adds the *interactive claim*
  layer and *claimed/pending visibility* on top — it does not change the once-ever rule.
- **"Past" due dates are time-based**, not payment-tracked: the app records when a payment
  recurs, never whether it was paid. The expanded view greys by date only.
- User-selected shapes: month-grouped calendar in a bottom sheet; launch popup fires for
  payments due within 3 days, at most once per day; tutorial is a guided card sequence
  (not spotlight/interactive); an unclaimed gift stays pending and is re-offered, never lost.

## 1. Due calendar sheet (v1.7.0)

### UI

- The Due Soon card on the Money screen (`app/money.tsx`) keeps its 5-item preview.
  The card header becomes tappable and shows a "View all ›" affordance; tapping opens
  **`DueCalendarSheet`** — a new modal bottom sheet component
  (`src/components/DueCalendarSheet.tsx`) following the `TransactionsSheet` pattern.
- Content is grouped by month, **from 3 months back to 12 months forward** (constants
  `DUE_CAL_MONTHS_BACK = 3`, `DUE_CAL_MONTHS_FWD = 12`; 12 forward guarantees every yearly
  payment appears exactly once). Each month section: header ("September 2026"), then one row
  per recurring payment due that month: group icon, name, resolved date ("Mon 15 Sep"), and
  the amount resolved for *that month* via the existing effective-dated helpers
  (`allocationAmountForMonth` for percent rows against that month's income;
  `allocationBaseAmountForMonth` for fixed rows). Yearly rows show their **full** amount in
  their due month — this is a payment calendar, not the ÷12 display equivalent.
- **Greying:** months before the current month are fully greyed; within the current month,
  rows dated before today are greyed; today onward renders normally. The sheet opens scrolled
  to the current month.
- Months with no due payments render nothing (skip empty sections).

### Logic

- New pure helper in `src/lib/allocationMath.ts`:
  `dueDateInMonth(a: Allocation, month: string): string | null` — monthly rows → clamped
  `due_day` in that month; yearly rows → clamped date only when `month`'s month-number equals
  `due_month`; one-offs and rows without `due_day` → null. No RN imports.
- Sheet is display-only in v1.7.0 (no row tap actions). Due Soon preview behavior and its
  5-item cap are unchanged.

## 2. Due-payments launch popup (v1.7.0)

### UI

- **`DueReminderSheet`** (`src/components/DueReminderSheet.tsx`): a launch popup card styled
  like `WhatsNewSheet` — "💸 Payments due soon" title, rows of name + friendly date
  ("today", "tomorrow", "in N days") + amount, single "Got it" button.

### Logic

- New pure helper `duePaymentsWithin(allocations, todayISO, horizonDays)` in
  `src/lib/allocationMath.ts` (or a sibling lib file): returns recurring payments whose
  `nextDueISO` falls in `[today, today + horizonDays]`, sorted by date. Horizon constant:
  **3 days**. This is the exact function the future native reminder scheduler will import.
- Show condition, evaluated on Home mount: helper returns non-empty AND
  `app_meta.due_reminder_last_shown !== todayISO()`. Dismissing stamps today into that key.
  Result: at most one popup per day, silent when nothing is due.
- **Popup ordering:** `WhatsNewSheet` gains an `onSettled` callback that fires once its gate
  resolves — after dismissal when it showed, immediately when it didn't. Home mounts
  `DueReminderSheet` gated on that callback, so the two launch popups never stack. No queue
  framework; one callback.

## 3. One-time tutorial (v1.7.1)

### UI

- **`TutorialSheet`** (`src/components/TutorialSheet.tsx`): one modal containing a sequence
  of ~7 Butter-narrated cards with progress dots, Back/Next buttons, and a Skip control:
  1. Meet Butter — tap Butter to log an expense (absorbs the old coachmark's message)
  2. Coins, streak & multiplier chips
  3. Shop & closet — spend coins, dress Butter
  4. Insights — trends & categories
  5. Money — income & set-asides
  6. Due dates & money history
  7. Backup in Settings + wrap-up
  Card copy is static (text + emoji; no live screen highlighting — RNW spotlight was
  explicitly rejected as fragile).

### Logic

- **Gating keys off the existing `coachmark_seen` app_meta flag.** Fresh installs
  (`coachmark_seen !== '1'`): `TutorialSheet` auto-shows instead of the old coachmark, and
  finishing OR skipping writes `coachmark_seen = '1'`. Existing installs already have the
  flag set, so nothing auto-shows — **no migration needed**.
- `Coachmark.tsx` is retired (deleted); the tutorial's first card replaces it. The
  `WhatsNewSheet` fresh-install seeding logic that reads `coachmark_seen` keeps working
  unchanged since the same key is written.
- **Replay:** a "Replay tutorial" row in Settings force-shows the sheet via a controlled
  `forceVisible`/`onForceClose` prop pair (same pattern `WhatsNewSheet` uses for dev preview).

## 4. Interactive streak gifts (v1.7.2)

### Data

- New `game_state.pending_chests` — JSON int-array string, default `'[]'`, holding milestone
  days earned but not yet claimed.
  - Native: `ALTER TABLE game_state ADD COLUMN pending_chests TEXT DEFAULT '[]';` in
    `database.ts`, try/catch-swallowed like the Phase 5f `claimed_chests` migration.
  - Web: field with `'[]'` default in `database.web.ts` seed + `queries.web.ts` normalizer
    (`g.pending_chests ?? '[]'`).
  - Backup: rides along inside the `game_state` snapshot automatically; import of an older
    backup without the field must default it to `'[]'` (both platforms' restore paths).
  - Dev data-reset clears it to `'[]'`.

### Award path (behavior change)

- In `updateGameStateAfterLog` — **mirrored in both `src/db/queries.ts` and
  `src/db/queries.web.ts`**, as the two files are today (the `computeLogUpdate` extraction
  stays in the hardening backlog; do not expand scope): reaching a milestone day no longer
  adds chest coins to the balance. Instead, if the day is in neither `claimed_chests` nor
  `pending_chests`, push it to `pending_chests`. Coins from the log itself are unchanged.
- `computeCelebration` in `useExpenseStore.ts` updates accordingly: `chestCoins` becomes a
  "chest earned this log" signal derived from the `pending_chests` diff (prev vs next)
  rather than the claimed diff.

### Claim flow

- **`ChestClaimSheet`** (`src/components/ChestClaimSheet.tsx`): popup card — "You hit a
  7-day streak! 🎁" with a large **Claim** button and a quiet "Later" dismissal. Home shows
  it after the log celebration finishes when a chest was just earned; it also re-offers on
  launch while anything is pending (most recent milestone shown when several are pending).
  On launch it joins the popup sequence last: What's New → due reminder → chest re-offer.
- Store action `claimChest(day)`: validates `day` is pending; moves it
  `pending_chests → claimed_chests`; `coins += chestFor(day)`; persists through the queries
  layer (both platforms); triggers coin-fly animation + success haptic.
- **Visibility:** the 🔥 streak chip shows a small 🎁 badge while `pending_chests` is
  non-empty. In `StreakSheet.tsx` each tier row's chest becomes stateful:
  claimed → muted "🎁 ✓"; pending → inline **Claim** button (calls `claimChest` in place);
  unreached → current locked style.

### Edge cases

- A streak reset never voids a pending chest — it was earned; it stays claimable forever.
- Multiple pending chests: all individually claimable in the streak sheet; the popup
  surfaces the most recent.
- Malformed JSON in either ledger parses to `[]` (existing try/catch style) — worst case a
  popup doesn't show; never a crash or double-pay. Double-claim is prevented by the
  pending-membership check inside `claimChest`.

## Error handling (all features)

- All flags go through the existing `getMeta`/`setMeta`; all JSON parses default to `[]`/
  absent on failure. Launch popups fail closed (don't show) on bad data; they never block
  the app.

## Testing & verification

- No test infra exists (known backlog) — verification is:
  - **Dev previews:** each new sheet (`DueCalendarSheet`, `DueReminderSheet`,
    `TutorialSheet`, `ChestClaimSheet`) gets a force-visible preview entry on `app/dev.tsx`,
    like `WhatsNewSheet`'s controlled mode.
  - **Manual checks at ~375×780** (user daily-drives on a phone): due calendar greying and
    month scroll; popup once-per-day stamp; tutorial fresh-install path (clear
    `coachmark_seen`) and replay row; full chest lifecycle (earn → later → badge → claim in
    sheet → claimed style; and earn → claim in popup).
  - Re-seed web test data after HMR (known Metro wipe behavior).
  - Pure helpers (`dueDateInMonth`, `duePaymentsWithin`) written RN-free so they're
    unit-testable when test infra lands.

## Release mechanics

- Opens **Phase 7** as three user-facing releases, each with its own What's-New entry:
  - **v1.7.0** — due calendar sheet + due-payments launch popup
  - **v1.7.1** — one-time tutorial + Settings replay
  - **v1.7.2** — interactive streak gifts (pending/claim + claimed visibility)
- Each release syncs, in lockstep: `docs/ROADMAP.md`, `src/constants/changelog.ts`,
  `scripts/gen-roadmap.mjs` mirror, `app.json` (version + build), and memory.
- ROADMAP notes these landed pre-native by explicit user call; the **phone-notification
  line stays under the native milestone**, now pointing at `duePaymentsWithin` as its
  ready-made selection logic. Native remains the top strategic priority after this session.
